# 库存计算输入与输出

Agent先接受用户的普通表格，再映射为下面结构；不要把JSON作为用户必须填写的资料。只读标准库脚本，不访问网络、不改原表、不发采购。

```sh
python3 scripts/inventory_plan.py input.json
```

输入表示**单个SKU、单个仓库、同一数量单位**。可对多个SKU分别计算，网络调拨与共享资金需要另外综合检查。日期均为YYYY-MM-DD；as_of是期初快照完成日，需求与到货在其之后、horizon_end之前或当天发生。日内顺序未建模，假设该日到货可在该日需求发生前使用，不能用于日内紧急交期承诺。

以下全部为合成数据：

```json
{
  "sku": "DEMO-A", "warehouse": "DEMO-W", "unit": "件",
  "as_of": "2026-01-01", "horizon_end": "2026-01-04",
  "opening_net_qty": "20", "safety_qty": "5",
  "moq": "12", "pack_multiple": "5", "lead_days": 3,
  "demand": [
    {"date": "2026-01-02", "qty": "10"},
    {"date": "2026-01-03", "qty": "10"},
    {"date": "2026-01-04", "qty": "10"}
  ],
  "receipts": [
    {"id": "DEMO-PO-1", "date": "2026-01-04", "qty": "10", "status": "confirmed"}
  ]
}
```

- 所有顶层字段必须提供。金额未参与此算术；数量可用十进制字符串保持精度。
- opening_net_qty已扣除需要扣的占用/冻结，不再次扣减。需求必须已处理预测与订单重叠。
- safety_qty、moq非负，pack_multiple正数，lead_days为非负自然日整数。工作日日历应由Agent另行换成实际最早可用日，不能直接把工作日数当自然日。
- demand按日唯一，未列日期视为已确认需求为零；存在缺失日期的未知需求时不得运行。receipts的id全局唯一，表示一次预计合格可用批次而非整个PO；同一PO分批用不同批次ID。
- confirmed表示预计可用数量/日期有依据，不表示实际已经收货。unconfirmed批次单列且不进入基准；用另一个明确标注的情景分析它。
- 日期在窗口外会拒绝，不偷偷丢弃；提前筛选后须告知未覆盖范围。数量最多100位有效数字、指数绝对值不超过100；不支持超大数字或无限窗口。

输出daily是基准逐日预计净库存，负值为累计未覆盖需求，不是实物数。建议数量只满足期末目标；regular_order_covers_timing同时检查新采购能否赶在基准首次缺货和目标截止前可用，不验证预算、供应商容量、日内先后或全部业务约束。regular_order_projection展示该采购最早可用时的模拟，不会修改基准。

脚本使用“未满足需求持续结转”的累计模型，不会自动判断流失销售或客户改期。业务采用流失销售模式时，应另做非负实物库存与服务损失逐期表；不能把脚本的期末负值直接当作仍需采购的欠单数量。规则不明时，脚本结果只标作持续欠交假设下的情景。

无Python时按planning-method.md公式生成相同逐期表，并注明未运行脚本。不能把无法运行脚本当成无法分析。
